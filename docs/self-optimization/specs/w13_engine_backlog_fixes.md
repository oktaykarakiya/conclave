# W13 Engine fixes: merge race, baseline bound, no-test-command paths, focus scan, repro-gate cancel, bug-fixer budget, resumed-session cost, failure reasons

Fix eight small engine flaws: merge race, unbounded baseline cache rows, housekeeping skipped on the no-test-command fast path and a mid-task test-command removal that passes the gate, a superlinear focus-marker scan, an uncancellable repro-gate retry, a bug-fixer session cap that counts usage-limit waits, a resumed Claude Code session whose cost is counted twice, and a failed task that never says why.

1. Merge race (`engine/task_merge.py::merge_task`). The checks run before `Orchestrator._merge` takes the per-target lock:
   - the task-branch lookup;
   - `target_sha`;
   - "already merged" (`merge-base --is-ancestor`).
   The returned `target_sha` is read after the lock is released. Two concurrent merges, or a merge racing a worker's own merge into the same target, can therefore pass the checks twice or report another merge's SHA. Required:
   - the checks, the merge and the SHA read happen under the same per-target lock `_merge` uses (refactor so the lock is taken once; no deadlock with `_merge`'s own acquisition);
   - the returned `target_sha` is the commit this merge produced;
   - a second concurrent `merge_task` for the same task returns the existing 409 "already merged" error and cleans up nothing twice.
   Test with two concurrent calls (asyncio.gather) on a real temporary git repo.
2. Baseline cache size (`db/repositories.py::save_baseline`). Since W2, the `baselines` table stores the full baseline failure output. Bound the stored text to `context.bulk_max_chars` of the project's effective config:
   - keep the head and the tail with the standard visible truncation marker from `engine/context_limits.py`;
   - this is recoverable bulk: it can be regenerated by re-running the command, so fitting it is allowed by the conventions;
   - emit the existing `context_truncated` event when it is cut.
   Test with output larger than the limit, and with output under it (unchanged).
3. No-test-command paths (`engine/orchestrator.py`).
   a. The early `no_test_command` return in `process_task` happens before the main `try`, so the task's `finally` housekeeping is skipped: event pruning (`retention_events_max`), baseline GC and whatever else that block does. Make the early-failure path run the same housekeeping, without creating a worktree.
   b. When the test command is removed from the config while a task runs, and `execution.allow_no_test_command` is false, the gate currently passes with a `gate_skipped_no_tests` log. It must fail the attempt with the same `no_test_command` reason and summary as the early check, never pass. With `allow_no_test_command: true`, keep today's logged pass.
   Tests for both.
4. Test-integrity scan complexity (`engine/test_integrity.py` or wherever the JS focus-marker scan lives). With thousands of `.only` / `fit(` / `fdescribe(` markers in one file, the scan is superlinear (measured: about 10 s for 6,000 markers). Make it linear in file size, with the same findings and output. Add a regression test that scans a file with 20,000 markers and asserts it finishes in under 2 s on CI (generous bound), and unit tests showing the findings are identical to the old implementation on representative inputs.
5. Repro-gate cancellation (`engine/repro_gate.py::_run_with_infra_retry` and its callers in `engine/bug_fixer.py`). The gate run and its one infra retry take no cancel event, so a bug-fixer cancel is seen only after the gate finishes. Thread the cycle's cancel event through:
   - no retry starts once cancelled;
   - a running gate command is stopped (process group killed, as the main gate does);
   - the outcome is a cancelled/infra result that changes no candidate status.
   Test: cancel during the first gate run → no retry, prompt return, candidate status unchanged.

6. Bug-fixer session budget and usage-limit waits (`runtime.py` `SessionBudget` and the bug-fixer worker loop).
   - W9 excludes usage-limit waits from each task's wall-clock budget. The bug-fixer session cap (`bug_fixer.wall_clock_budget_minutes`, which defaults to `execution.wall_clock_budget_minutes`) still counts them, so a session can end during a long wait for a weekly reset.
   - Exclude the time the session's dispatches spent waiting. The quota gate's wait tracking (`WaitTracker`, `AgentRunner.quota_waited_seconds`) already measures it.
   - Test: a session whose hunter dispatch waits longer than the session budget does not end for budget; with an injected clock, nothing sleeps.

7. A resumed session's cost is counted twice (`providers/quota.py::dispatch_with_quota`, with a per-engine fact from the providers).
   - MEASURED on the live daemon (2026-11-17, W17's planner). A five-hour limit interrupted the planner after 71 turns, and the run reported `total_cost_usd` 4.52. After the reset, `dispatch_with_quota` resumed the session; that run took 18 turns and reported 8.49. Claude Code's `total_cost_usd` is the session's running total, and a `--resume` run continues it (the CLI's own result schema text says a resumed session's first result already includes the earlier turns' cost). Conclave stored two usage rows, 4.52 (`QuotaEvents.waiting`) and 8.49 (`AgentRunner`): 13.01 for a planner that cost 8.49. The turn and token counts are per run and are right as they are.
   - opencode is not affected: `opencode_cli` sums the `step_finish` costs of the run's own stream.
   - Fix: when a dispatch continues a session whose earlier run already reported a running total, the continued run's `AgentResult.cost_usd` must become its own share (its running total minus the total already reported for that session, never below 0). Both the result passed to the listener as `interrupted` and the final result get this treatment, so every usage row is that run's own cost and the rows sum to the session's real total. Two waits in one session: 4.52, then 6.00, then 8.49 become 4.52, 1.48, 2.49. When the engine no longer knows the session and the dispatch starts afresh, the fresh session's cost counts in full.
   - Only engines whose cost is a session running total get this. Make that a fact the provider states for the dispatch's engine (Claude Code: yes; opencode: no), not a check on the model name in `quota.py`. Keep it working through the engine router.
   - The planning-session turn and every other `dispatch_with_quota` caller get the fix through the shared function.
   - Tests:
     - fake `claude` executable: a refused run with running total 4.52, then a resumed run with 8.49, gives interrupted 4.52 and final 3.97;
     - two refusals in one session give 4.52, 1.48, 2.49;
     - an unknown session followed by a fresh run gives the fresh run's full cost;
     - an opencode-style provider's per-run costs pass through unchanged;
     - an integration test over the orchestrator: the task's usage rows sum to the session's final running total.

8. Why an attempt and a task failed (`engine/orchestrator.py`).
   - MEASURED on W12's branch (pilot hidden test): a task whose mandatory `security` reviewer never gave a verdict ends with `result_summary` "failed (max_retries) after 3 attempt(s)", and each `attempt.failed` event is only `{"n": k, "stage": "review"}`. The reason ("REVIEW INCONCLUSIVE ... SECURITY: ...") reaches the next developer prompt and a `grounding.warning`, but neither the attempt events nor the task row. A developer failure carries `error` and an infra gate failure `reason`; a review failure and a red gate carry nothing.
   - Every `attempt.failed` event carries `reason`: one line, at most 300 characters, whitespace collapsed. For a review failure, say which reviewers blocked and why, with each reviewer's own reason cut short: for example "rejected by SECURITY (fail): <reason>", "inconclusive: mandatory reviewer(s) SECURITY gave no usable verdict", "no reviewer returned a usable verdict". For a red gate, "<label> gate not green (exit N)". For a developer failure, its error. Keep every existing payload key.
   - A failed task's `result_summary` ends with the last attempt's reason: "failed (max_retries) after 3 attempt(s); last: <reason>". Timeouts and the planner note from W12 keep working and stay in the summary.
   - Update the pilot guide's monitoring section: `attempt.failed` has `reason`, and the failure summary names the last attempt's reason.
   - Tests (fake provider): a mandatory reviewer that never answers (the failed task's events and summary name the reviewer); a reviewer `fail` verdict (the attempt's reason names the reviewer and quotes its reason); a red gate (the reason states the exit code); the 300-character bound with a long reviewer reason.
