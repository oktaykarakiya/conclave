# W20 Backlog leftovers: reviewer baseline, REST unknown ids, cancel and approval races, graph writers

Fix the six open backlog items the audits reported (`docs/self-optimization/backlog.md`, items 3–7 and 9). Items 1, 2 and 8 stay out of scope (they need an outside measurement, a funded account, or are a new feature).

Work like the audits: for each item, first demonstrate it with a deterministic failing test (FakeProvider, temporary homes, no network, never the live daemon), then make the smallest fix. An item marked "suspected" that you cannot demonstrate is not fixed: change nothing for it and say why in your final message. End with a FINDINGS list (file:line, the failing scenario, the fix, the test) and a NOT REPRODUCED list.

REQUIRED
1. Reviewers never get the baseline preamble (backlog 4; `engine/orchestrator.py`, `engine/baseline.py`). `baseline.py` says the baseline exists "so reviewers do not blame pre-existing failures on this task's diff", and `build_baseline_preamble`'s text speaks to reviewers ("do NOT block on these — only block if YOUR diff introduces NEW failures"), but only the developer and the planner receive it (`_baseline_preamble` at the developer prompt and the planner prompt). A reviewer that runs the suite and sees a pre-existing failure can fail the attempt for it.
   - Every reviewer prompt (parallel or sequential, any reviewer node, every re-run) carries the same preamble when the baseline has failures, fitted for that reviewer's node through `_baseline_preamble` (the same `context.*` limit, marker and event as for the developer); none when the baseline is green or absent.
   - Tests: with a red baseline, every reviewer prompt contains the pre-existing failure; with a green baseline, none contains the preamble.
2. Unknown ids answer 200 on REST where MCP answers `isError` (backlog 6; `web/api.py`). Measured on the live daemon: `GET /api/projects/<unknown>/tasks`, `GET /api/projects/<unknown>/quarantine` and `GET /api/tasks/<unknown>/events` answer 200 with an empty list; `DELETE /api/projects/<unknown>` answers `{"detached": ...}` and emits `project.deleted` for a project that never existed; `POST /api/projects/<unknown>/pause` and `/resume` answer 200 and record state for it. Each answers 404 for an unknown id, with nothing emitted or recorded. Check every caller in `frontend/src` first: if the SPA relies on a 200 for an id it just deleted, handle the 404 there (and rebuild the SPA); never make a UI page error out for a project or task that was deleted while it was open. Also check `/projects/{id}/quarantine/integrity` and `/planning/sessions/{id}/tasks` and treat them the same way if they have the defect.
   - Tests: each route above with an unknown id answers 404 and emits nothing; with a known id the answers are unchanged.
3. The cancel fallback for a task waiting for approval writes unconditionally (backlog 9; `web/api.py` `cancel_task`, and the MCP `conclave_cancel_task` if it has the same shape). When `request_cancel` finds no running dispatch and the task read earlier was `waiting_for_approval`, it sets `cancelled` without checking the state is still `waiting_for_approval`: an approval landing in between is overwritten. Use a conditional update, like A3's `cancel_task_if_pending`, and answer for the task's current state when it no longer matches. Test: the approval lands between the read and the write (patch `request_cancel` to approve the task, then return false); the task is not overwritten to `cancelled` and the answer says what happened.
4. An operator node override can apply to a later attempt (backlog 3, suspected; `web/api.py` `complete_task_node`, MCP `conclave_complete_node`, `engine/orchestrator.py` `_await_human_approval` and `_approval_resolutions`). A completion posted while the node is not paused is stored per (task, node) without an attempt, and the next non-paused `_await_human_approval` of that node, in any later attempt, consumes it. Demonstrate it; if confirmed, a resolution applies only to the attempt it was posted for (the body's `attempt`, else the node's latest checkpoint attempt, as the endpoint already computes), and one for an earlier attempt is dropped with a `log` event saying so.
5. A swarm double-claim window (backlog 5, suspected; `engine/orchestrator.py` `_await_human_approval`, around the `waiting_for_approval` state change). The task is set `waiting_for_approval`, then two events are emitted, and only then is its waiter registered. An approve that lands in between sets the stored state to `approved`, which a worker tick with `max_parallel_tasks` > 1 can claim and run a second time. Demonstrate it (make an emit yield and approve during it); if confirmed, register the waiter before the state is written, so the approve reaches the waiting run and the stored state never reads `approved` for a task that is still running.
6. Whole-graph writers are last-writer-wins against MCP graph edits (backlog 7; `web/api.py` `PUT /api/projects/{id}/workflow`, `engine/workflow_evolver.py` `_compare_and_apply`, `mcp/tools.py` `_graph_edit_lock`). A3 serialised the four MCP graph-edit tools under one lock per `Database`, but REST's whole-graph `PUT` and the evolver's compare-and-apply do not take it, so an MCP edit that read the graph before them and saves after them silently undoes their change, or theirs undoes it. Every writer of a project's workflow graph takes the same lock (move it to a module both import if needed, keeping the lock order graph → config → database), and the evolver compares and applies under it. `PUT` stays a whole replacement by design. Test: an MCP node upsert racing a REST `PUT`, and one racing an evolver apply, both end with a graph that is exactly one of the two serial outcomes.
