# W19 Audit follow-ups: settings-proof isolation, shared-worktree reviewers, retry bounds, operator SQL

Fix what the audits (A1 providers, A2 engine, A3 MCP/web/database) and the pilot found while running them, but could not or should not fix inside an audit.

REQUIRED
1. Isolation that a settings file cannot undo (`providers/profiles.py`, `providers/claude_cli.py`). Found by A1, verified against Claude Code's documentation (code.claude.com/docs/en/settings, "Settings precedence"): an `env` block in `.claude/settings.json` or `.claude/settings.local.json` is applied over the inherited environment, and in a git worktree Claude Code reads `settings.local.json` from the main checkout's root. So the repository's settings, or a file a worker writes there during the task (reviewers share the worktree), can set `CLAUDE_CODE_DISABLE_AUTO_MEMORY=0` or turn background tasks, cron or `CLAUDE.md` loading back on for the next dispatch. Settings passed with `--settings` outrank the local and project files.
   - For an isolated Claude Code worker, also pass the isolation variables (`_ISOLATION_ENV`) as `--settings '{"env": {...}}'` (JSON on the command line, no file), so no project or local settings file can override them. Keep W8's decision that the repository's project and local settings otherwise apply (permissions, hooks).
   - `profile.extra_env` still wins: a variable the operator sets in `extra_env` that is also an isolation variable goes into the `--settings` env with the operator's value.
   - A non-isolated worker is unchanged (no `--settings`).
   - Tests: the isolated invocation carries the `--settings` env with every isolation variable; `extra_env` overrides one of them there too; a fake `claude` that applies a worktree `.claude/settings.local.json` env over its environment and then `--settings` (in that documented order) ends with the isolation values; non-isolated runs have no `--settings`. Update AGENTS.md's worker-isolation bullet and the pilot guide.
2. Parallel reviewers share one worktree (`engine/orchestrator.py`). Found live in A1's review: the tester and the reviewer temporarily swapped the base versions of two files into the worktree to prove the new tests fail on base, while the risk reviewer ran the full suite in the same worktree, which then showed 14 unexplained failures (green on its next two runs). The commit is safe (the reviewed tree is restored before the gate, `ENG-2`), but a verdict can rest on another reviewer's experiment.
   - Every reviewer prompt Conclave builds (parallel or sequential, any reviewer node) states, in Conclave's own text (not the editable persona): the worktree is shared with the other reviewers and the gate; do not change, add or delete any file in it, not even temporarily; to run code against another version (the base, a variant), work in your own copy outside the worktree (for example `git worktree add <scratch> <rev>` or `git archive <rev> | tar -x -C <scratch>`) and remove it afterwards.
   - After the reviews of an attempt, compare the worktree (staged as for the review tree, caches and `.venv` excluded) with the tree that was reviewed. If they differ, emit `review.worktree_modified` with the attempt and the changed paths (at most 50, with the total count), then restore as today. The pilot guide lists the event and what it means (a verdict may rest on a disturbed run).
   - Tests: the reviewer prompt carries the rule; a fake reviewer that edits a tracked file and creates a new one yields `review.worktree_modified` with both paths, and the committed tree is still the reviewed one; an attempt whose reviewers change nothing emits no such event.
3. An absurd usage-limit reset (`providers/quota.py`, from A1). A reset time reported more than 8 days ahead (beyond any Claude Code window; for example a `retry-after` in milliseconds read as seconds) keeps the engine's gate closed until then, and only a cancel or a restart recovers. Treat a reset more than 8 days in the future as unknown: the gate closes for `quota_retry_minutes`, as for a missing reset, and the `quota.waiting` event says the reported reset was ignored. Tests: a reset 30 days out waits `quota_retry_minutes`; a reset 6 days out (a weekly window) is kept.
4. Retry limits that do nothing (`engine/orchestrator.py`, from A2). The attempt loop is bounded only by the developer's `max_retries` (default 3). `execution.review_rounds_max` (default 20, "max review rounds per task", listed in the pilot guide's key fields, the MCP `conclave_patch_config` schema and the Settings UI) is never read, nor is an `on_fail` edge's `max_iterations` ("Bound on retry loopback edges", shown on the workflow canvas, and raised by the evolver's grow). Make every one of them a real bound, the tightest winning:
   - a task makes at most `review_rounds_max` attempts that reach review;
   - a retry that follows an `on_fail` edge back to the developer is taken at most `max_iterations` times for that edge (attempt 1 plus at most `max_iterations` retries through it);
   - the developer's `max_retries` stays the overall attempt bound.
   With the defaults (3, 3, 20) and with this project's graph (edges at 6) the behaviour is unchanged; test that too. When a bound other than `max_retries` ends the task, the failure summary names that bound and its value. The pilot guide says how the three combine and that raising `max_iterations` only matters when that edge is the tightest bound.
   - Tests: `review_rounds_max: 1` with three failing review rounds stops after one; an edge with `max_iterations: 1` stops after one retry through it while another failing reviewer's edge still allows its own; the defaults still make three attempts.
5. No prompt content twice, no copy per brace (from A2's performance review).
   - Since A2, a retry prompt carries each rejected attempt's diff in the attempt history (`engine/memory.py`) and the latest one again in full as the prior-diff block, so the newest rejected diff is sent twice. Its history entry should point to that block instead of repeating it (for example "Diff produced: shown below as YOUR IMMEDIATELY PRIOR DIFF"), and earlier attempts keep their own diffs. Nothing is cut: every diff still appears once, fitted as today.
   - `parse_verdict`'s bare-JSON fallback (`engine/verdict.py`) copies the rest of the reply at every `{` (`log_text[idx:]`). Decode in place with `JSONDecoder.raw_decode(log_text, idx)` and the same results.
   - Tests: a third-attempt developer prompt contains attempt 2's diff exactly once and attempt 1's diff once; the parse results are unchanged on the existing verdict tests, plus one reply with many braces before its verdict.
6. The test double misreads the post-mortem (`tests/integration/fake_provider.py`). `FakeProvider.role_of` recognises the post-mortem only by "Post-Mortem Agent", the heading of its seeded persona; in a test without seeded personas the post-mortem prompt starts "You are the postmortem agent of" and is classified as `developer`: a test scripting `replies={"developer": ...}` or counting developer prompts also gets the post-mortem's. Make `role_of` return `postmortem` for it (and `post_mortem_calls` count it), and check that no existing test relied on the misreading.
7. Operator SQL that can stall the daemon or read secrets (`db/repositories.py` `query_interaction_logs_readonly`, used by `POST /api/observability/query` and `conclave_query_interactions`; from A3). The query runs on the daemon's one shared connection with no time limit, so a heavy query blocks every database call of the daemon, and it can read the `secrets` table, whose values no other endpoint returns. The database is in WAL mode, so a separate reader never blocks the writer.
   - Run each query on its own read-only connection (`file:...?mode=ro`, URI), off the event loop (a worker thread), never on the shared connection.
   - A deadline: a progress handler aborts a query that runs longer than 10 seconds; the answer is a 4xx / `isError` saying the query took too long, and the connection is closed.
   - An authorizer refuses reading the `secrets` table (and nothing else that works today): a query that touches it is a 4xx / `isError` naming the table. Keep the existing keyword guard.
   - The result shape (`columns`, `rows`, `row_count`) and the row limit stay as they are. Pilot guide: say the query runs read-only with a 10-second limit and cannot read secrets.
   - Tests: a query on `secrets` (directly, in a subquery, in a `WITH`) is refused; a query that never ends (a recursive CTE) stops at the deadline (patch the deadline short in the test) while another database call made meanwhile completes; an ordinary query returns the same answer as before.
8. Two small input contracts (from A3).
   - Attaching a project with a `config_preset` or `workflow_template` that does not exist (`POST /api/projects`, `conclave_attach_project`) silently ignores it: answer 422 / `isError` naming the unknown preset or template, with nothing attached.
   - The stdio bridge (`mcp/__main__.py`) answers a JSON-RPC notification (a message without an `id`) with an error object when the daemon errors or times out; JSON-RPC forbids answering a notification. Send nothing for a notification on those paths.
   - Tests for both.
